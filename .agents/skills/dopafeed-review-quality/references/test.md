# Test の確認項目

節番号は『コードレビューで学ぶ Ruby on Rails 第三版』に対応する。RSpec と FactoryBot を使い、Dopafeed 固有の振る舞いが壊れたときに検知できるかを確かめる。

- `describe`、`context`、`it` を読んで、何をどの条件で実行し、何が起きるべきか分かるか。「正しいこと」のような記述は具体的な結果が伝わるかを確認する（§4.1、§4.2、§4.13）。
- 準備、実行、検証の順で読めるか。必要な入力と期待値の根拠が例の中にあり、期待値を実装と同じ式で再計算していないか（§4.3、§4.7、§4.15）。
- `let`、`let!`、`before` が、実行の順序や副作用を隠していないか。ローカル変数や関係する setup を使い、テストに必要な値と分かりやすい評価値に絞れているか（§4.6、§4.16、§4.18）。
- system spec は 390×844 の利用者操作の後、変わるべき表示や状態まで確認しているか。スタイルが仕様の場合を除き、ロール、ラベル、安定した要素を使い、装飾クラスの変更で壊れないか（§4.4、§4.5）。
- アプリ固有の規則と境界を検査しているか。Rails やライブラリの標準動作だけを再確認する spec と、変更で壊れる振る舞いを見逃さない spec を見分ける（§4.8）。
- 通常の factory は保存可能な最小の状態か。モデル・DB の既定値を重ねて定義していないか。意味のある共有状態は trait で指定し、その例の結果を左右する値が見えるか（§4.9、§4.10、§4.11）。
- 表示・更新・ジョブ起動が起きないことを検査する場合、起きるべき入力の対照ケースもあり、誤った画面や対象 ID でもテストが通ってしまわないか（§4.12）。
- フォームと Strong Parameters の変更では、必要な属性が実際に保存され、許可されない属性が更新されないことを request spec 等で確認できるか。テスト環境で未許可のパラメータを検知する設定も確認する（§4.14）。
- 非同期表示は Capybara の待機つきマッチャーで結果を待てるか。固定時間の `sleep` で処理の速さに依存していないか（§4.17）。
- モデル、リクエスト、ジョブ、システムのうち、失敗を捉えられる最小の層を選べているか。重要な操作は画面で通し、外部通信を既存の VCR / WebMock で隔離しているか（§4.19）。
