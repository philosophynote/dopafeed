# Model の確認項目

節番号は『コードレビューで学ぶ Ruby on Rails 第三版』（中谷一郎、登川仁至、田中義人、2026年）に対応する。差分に関係する項目を選び、SQLite と Dopafeed の仕様に照らして影響を確かめる。

## データの意味と整合性

- 中間モデルの名前から、どのレコードを結ぶかに加えて、保存、読了、判定などの関係の意味が分かるか（§1.1）。
- 権限の異なる主体を追加する場合、それぞれの属性、認証とデータ参照の境界が明確か（§1.2）。
- 新規レコードの既定値が `attribute` や DB の適切な層で定義され、読み込んだ既存行の `NULL` や旧値が意図せず置き換わらないか（§1.4）。
- マイグレーションを新規 DB と既存 DB の両方に適用できるか。当時のテーブル定義で動く SQL などを使い、可変のアプリモデルに依存する箇所を確認する（§1.5）。
- Rails のバリデーションと SQLite の `NOT NULL`、一意制約、外部キーなどが一致するか。別経路からの書き込みや並行更新でも保護されるか（§1.8）。
- 保存・削除時のコールバックが発火する全経路を調べる。外部 I/O や通知は起動条件とコミット後の扱いが明示されているか（§1.9）。
- 日付境界を扱う処理は時刻とタイムゾーンを揃えており、時刻を渡すか固定して検証できるか（§1.11）。
- 親の削除で保護すべき子が消えないか。`dependent`、DB の削除ルール、コールバックと大量削除時の負荷を確かめる（§1.12）。
- 複数の操作に散らばるドメインの計算や判定が、意味のある単位にまとまっているか。現在の使い方から切り出す理由を説明できるか（§1.15）。
- 複数行を変更する処理の途中で失敗したとき、全体がロールバックされるか。暗黙のトランザクションの範囲と、コミット後に必要な副作用を確認する（§1.18）。
- バリデーションが不正な入力の保存を防ぎ、追加・強化した制約が既存データの読み書きにどう影響するか（§1.21）。

## クエリと非同期処理

- `default_scope` で呼び出し元に見えない絞り込みや順序が追加されると、取得・更新・削除対象にどう影響するか。`scope` の返り値は空の場合も連鎖できる `Relation` か（§1.3、§1.10）。
- 集計や列だけの取得で大量のレコードを Ruby にロードしていないか。DB 側で処理した場合の `NULL`・重複・並び順を含めて確認する（§1.6）。
- `has_many` の JOIN で行が増幅しないか。絞り込みに JOIN が要るかを確認し、別クエリで関連を読む `preload` と比較する（§1.7）。
- 実際に発行される SQL、JOIN 条件、件数、重複、索引を確認する。ループ内で `where`、`exists?`、`count` などが関連の読み込み済みデータを迂回していないか（§1.13、§1.16）。
- 短絡評価の順序を変える提案は、条件が独立しており、副作用と例外の扱いが等しいときに検討する。SQL や通信が不要なケースで先に判定できるか（§1.14）。
- Job にある処理のうち、キューの引数・再試行・失敗の記録と、モデルやサービスに置ける業務処理の境界が明確か（§1.17）。
- 大量データは `find_each` や `in_batches` でメモリとロック時間を抑えられるか。バッチの順序と再実行で行を飛ばしたり重複処理したりしないか（§1.19）。
- 外部 API の待ち時間、失敗区分、再試行の上限と利用者に見える結果を確認する。再試行により送信・予算消費・DB 更新が重複するかを追う（§1.20）。
