# Ruby と設定の確認項目

節番号は『コードレビューで学ぶ Ruby on Rails 第三版』に対応する。リポジトリの規約と差分の具体的な影響を根拠に判断する。

- seed やバッチの登録が部分的な失敗で成功扱いにならないか。`create!` などで失敗を知らせ、途中の状態と再実行時に起きることを確認する（§5.1）。
- 開発、テスト、CI、本番で DB・キュー・外部サービスの前提が異なる場合、分岐と検証の対象が分かるか。設定名や環境変数の契約は値を読まずに確認する（§5.2）。
- `nil` が来る経路を特定できるか。必須の値の欠損が `&.` や早期 return で隠れていないか（§5.3）。
- 空の Ruby ファイルや実体のない spec が残り、機能や検証が存在するように見えていないか。生成物や配置用ファイルは用途を確認する（§5.4）。
- 通常の入力による分岐と予期しない例外を区別できるか。`rescue` の範囲や捕捉する例外が広く、処理の失敗を隠していないか（§5.5）。
- 動的ディスパッチで呼び出し元と呼び出し先を追えるか。`send` や `public_send` の候補が入力で変わる場合は、明示した許可リストに収まるかを確認する（§5.6、§5.14）。
- Gemfile の固定に理由があり、必要な更新を取り込めるか。Gemfile.lock の再現性と、CI・配布物を固定するセキュリティ要件は引き続き守る（§5.7）。
- Ruby 標準の `Enumerable` や、採用している版の Rails・ライブラリが提供する API で処理を表せるか。同じ入力、返り値、エラーの意味になるか確認する（§5.8、§5.13）。
- 現在の要件に沿った変更か。推測で追加した拡張点や複数の責務が、現在の呼び出しや検証を複雑にしていないか（§5.9、§5.11）。
- 名前から処理の条件、返すもの、副作用が分かるか。肯定形にできる分岐は読みやすさを確認し、内部メソッドは実際の呼び出し元に合わせた可視性かを確かめる（§5.10、§5.12、§5.15）。
- コメントは実装やテストから分からない制約や判断の理由を説明しているか。ADR 0009 と `AGENTS.md` を使い、規約・不具合の指摘には具体的な根拠を添える（§5.16、§5.17）。
