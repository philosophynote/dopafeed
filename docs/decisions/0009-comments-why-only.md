# ADR 0009: コードコメントは「なぜ」だけ書く
日付: 2026-11-01 状態: 採用（Unit 3.5 で規約化。既存コメントの掃除と構造テストは #24）

nao の決定。伊藤淳一氏の記事「AIにありがちな『イマイチなコードコメント』9パターン」（https://qiita.com/jnchito/items/636c519c0b1d347c79b7 ）を Unit 0〜3 の app/ と lib/ に当てたところ、型 1（読めばわかる）・3（経緯や工程）・4（呼び出し元の列挙）・8（重複）・9（責務外、ここでは画面の話）がはっきり出ており、型 2（書く場所）と 7（読んで疑問が増える）も軽く出ていた。原因は AI の性分ではなく、ADR 0007 の「`@param` / `@return` / `@raise` / `@yield`」が「毎メソッドに書け」と読めたことと、reviewer と PR テンプレにコメントを見張る項目が無かったこと。良いコメント（`parse` で Nokogiri の strict を先に通す理由、`MAX_REDIRECTS` を dopamine.yml に置かない理由）は同じ AI が既に書けていた。

- 規約の本文は AGENTS.md の「規約」。reviewer と PR テンプレはそこを参照する（規約の文面を複数の場所に写さない）
- 当初は「なぜそうするか」とクラス・モジュール冒頭の 1 行要約を求めていたが、2026-11-10 の nao の指示で見直した。要約の必須化が自明な説明と余計な差分を増やしたため、冒頭要約の必須規則を廃止し、コメントには別の方法を採らない理由だけを残す。対象を app/・lib/ の Ruby から JavaScript・ビュー・設定・テスト補助コードにも広げ、既存の不要なコメントを整理する
- `@param` / `@return` / `@raise` / `@yield` は、名前と型を日本語に言い換えるだけ（`@return [Boolean] 完読したか` の下が `completed_at.present?`）なら書かない。判断の基準は「型と名前を読んだ人が知らないことを足しているか」
- 書かないもの。工程（Unit 番号・陣・「別 PR で」。Issue と PR に書く）。画面名（モデル・サービス・ジョブは画面を知らない。app/views と docs/screens に書く）。呼び出し元の列挙（「{FetchFeedJob} からだけ呼ぶ」。守らせたいなら spec/structure/ のテストで落とす）。呼ぶ側と呼ばれる側への同じ説明（定義側に残す）
- 見張り。.claude/agents/reviewer.md の検査項目と .github/pull_request_template.md の確認欄。ルールだけでは AI は 100% 守らないので、最後は nao がマージ前に見る
- 既存の app/ と lib/ のコメント（Unit 0〜3 で 10 行）の掃除と、コメントに工程・画面の語を禁じる構造テストは #24。触ったファイルから直す
